### Algorithms JHU 605.621 82 — Spring 2026


This assignment uses implementations of Quicksort in both Python and Java, testing performance
across a range of input sizes (1 to 10 million integers) and two partition strategies.
The benchmark compares wall-clock sort time for random and already-sorted inputs,
which exposes the stark difference between average-case and worst-case behavior.

| File | Description |
|------|-------------|

| `test_input/` | Directory of generated CSV input files, named by size and type (e.g. `ten_thousand_random_ints.csv`, `one_million_sorted_ints.csv`). |

## Generating Test Input Files

### `generate_random_ints_csv.py`

Generates a single list of `x` comma-separated integers and prints it to stdout.

```shell
# 10 random integers between 1 and 100,000
python generate_random_ints_csv.py 10

# 10 integers sorted ascending: 1, 2, 3, ..., 10
python generate_random_ints_csv.py 10 --sorted

# 10 integers sorted descending: 10, 9, 8, ..., 1
python generate_random_ints_csv.py 10 --reverse
```

| Parameter | Description |
|-----------|-------------|
| `x` (positional) | Number of integers to generate (required) |
| `-s`, `--sorted` | Output integers in ascending order from 1 to x |
| `-r`, `--reverse` | Output integers in descending order from x to 1 |

`--sorted` and `--reverse` are mutually exclusive. If neither is given, random integers
in the range [1, 100,000] are generated.

### `generate_test_inputs.py`

Generates the full suite of test input files used by the benchmark.
Creates `test_input/` if it does not exist, then generates a random and a sorted CSV
for each power of 10 from 10⁰ to 10⁷, named using English words:

```shell
python generate_test_inputs.py
```

Output files created in `test_input/`:

| File | Contents |

| `one_sorted_ints.csv` | 1 integer, sorted |
| `ten_random_ints.csv` | 10 random integers |

## Running Quicksort

Both implementations share the same command-line interface.

### Parameters

| Flag | Description |
|------|-------------|
| `-f`, `--file <FILE>` | Read input from a file. If omitted, reads from stdin. |
| `-p`, `--partition <METHOD>` | Partition strategy: `default` or `median-of-three` (default: `default`) |
| `-s`, `--suppress` | Suppress sorted output. Useful for benchmarking where only timing matters. |
| `-h`, `--help` | Print usage and exit. |

### Python

```shell
# From a file
python quicksort.py -f test_input/one_million_random_ints.csv

# From stdin
cat test_input/one_million_random_ints.csv | python quicksort.py

# Use median-of-three partition (better on sorted input)
python quicksort.py -f test_input/one_million_sorted_ints.csv --partition median-of-three

# Suppress output (just sort, don't print results — useful for timing)
python quicksort.py -f test_input/one_million_random_ints.csv --suppress

# Time it
time python quicksort.py -f test_input/one_million_random_ints.csv --suppress
```

### Java

First compile (only needed once):

```shell
javac QuickSort.java
```

Then run with `-Xss64m` to increase the JVM thread stack size (see section below):

```shell
# From a file
java -Xss64m QuickSort -f test_input/one_million_random_ints.csv

# From stdin
cat test_input/one_million_random_ints.csv | java -Xss64m QuickSort

# Use median-of-three partition
java -Xss64m QuickSort -f test_input/one_million_sorted_ints.csv --partition median-of-three

# Suppress output and time it
time java -Xss64m QuickSort -f test_input/one_million_random_ints.csv --suppress
```

### File input vs stdin

Both implementations default to reading from **stdin** if no `-f`/`--file` argument is
provided. This allows piping directly from the generator:

```shell
python generate_random_ints_csv.py 100000 | python quicksort.py
python generate_random_ints_csv.py 100000 | java -Xss64m QuickSort
```

The `--suppress` flag discards the sorted output entirely. Since printing a million
comma-separated integers to the terminal is slow, suppressing it isolates the sort
time from I/O time when benchmarking.

## Stack Overflow Handling

Recursive quicksort has O(n) worst-case call stack depth, which occurs when the input
is already sorted and the `default` (last-element) pivot is used — every partition step
produces one empty side and one side of n−1 elements, so the recursion goes n levels deep.
Both implementations address this, but in different ways.

### Python — `sys.setrecursionlimit` + enlarged thread stack

Python imposes two separate limits on recursion depth:

1. **Python-level frame limit** — controlled by `sys.setrecursionlimit()`. The default
   is 1,000 frames, far too shallow for large inputs. The script raises this to 1,000,000.

2. **OS thread stack size** — the physical memory allocated for the call stack. The
   default main thread stack is typically 1–8 MB depending on the OS, and cannot be
   resized after the process starts. When it runs out, the process receives a hard
   segmentation fault — not a catchable Python exception.

The fix is to spin up a **new thread** with a larger stack before any recursion happens.
New threads can be given an arbitrary stack size via `threading.stack_size()` before
they are created. The entire `main()` function — and therefore all of quicksort's
recursive calls — runs inside this thread (see [2])

```python
import threading
import sys

sys.setrecursionlimit(1000000)          # raise Python's frame limit

def main():
    # ... all argument parsing, input reading, and quicksort happen here

if __name__ == "__main__":
    threading.stack_size(64 * 1024 * 1024)  # request a 64 MB stack for new threads
    thread = threading.Thread(target=main)
    thread.start()   # launch main() in the new thread with the larger stack
    thread.join()    # wait for it to finish before the process exits
```

`thread.join()` makes the main thread block until the worker finishes, so the program
behaves identically to a direct call to `main()`.

### Java — `-Xss` JVM flag

Java's default thread stack is typically 512 KB–1 MB depending on the platform and JVM.
Unlike Python, there is no separate interpreter-level frame limit — just the physical
stack memory. The JVM provides the `-Xss` flag to set the stack size for the main thread
at startup:

```shell
java -Xss64m QuickSort -f input.csv   # 64 MB stack
```

Common values:

| Flag | Stack size | Use case |
|------|-----------|----------|
| `-Xss8m` | 8 MB | Modest bump from the ~512 KB default |
| `-Xss64m` | 64 MB | Handles very large sorted inputs comfortably |
| `-Xss512m` | 512 MB | Extreme cases |

To avoid passing the flag every time you can set it via an environment variable:

```shell
export JAVA_TOOL_OPTIONS="-Xss64m"
java QuickSort -f input.csv
```

## Partition Strategies

Both implementations support two partition strategies selected via `-p` / `--partition`.

### `default` — Last-element pivot (default from CLRS Chapter 7 [1])

Uses `A[r]` (the last element of the subarray) as the pivot. Every element is compared
against the pivot and moved to the low side if it is ≤ pivot, otherwise it stays on the
high side. The pivot is then placed in its final sorted position.

```
pivot = A[r]
scan left to right: if A[j] <= pivot, swap into low side
place pivot at boundary
```

Simple to implement and fast in practice on random data, but has a critical weakness:
when the input is **already sorted** (ascending or descending), the pivot is always the
largest or smallest element, producing maximally unbalanced partitions — one side of
n−1 elements and one side of 0 — every single time.

### `median-of-three` — Median pivot

Looks at three elements — `A[p]` (first), `A[(p+r)/2]` (middle), and `A[r]` (last) —
sorts them in place to find the median, then swaps the median into the last position and
proceeds identically to the default partition.

```
sort A[p], A[mid], A[r]  →  A[p] ≤ A[mid] ≤ A[r]
swap A[mid] into A[r]    →  A[r] is now the median
proceed with Lomuto partition as normal
```

On sorted or nearly-sorted input the median of the first, middle, and last elements is
the middle element, which splits the array in half — giving O(log n) recursion depth
instead of O(n). On random data the improvement is modest but consistent.

## Complexity Analysis

### Default partition

| Case | Input type | Time complexity | Recursion depth | Notes |
|------|-----------|-----------------|-----------------|-------|
| Worst case | Already sorted (asc or desc) | O(n²) | O(n) | Pivot always min or max; one side always empty |
| Average case | Random | O(n log n) | O(log n) | Pivot splits array roughly in half on average |
| Best case | Random / balanced | O(n log n) | O(log n) | Pivot always splits exactly in half |

The worst case is directly observable in the benchmark: the `*_sorted_ints.csv` files
with `--partition default` will be dramatically slower than the same files with
`--partition median-of-three`, and dramatically slower than the random files of the
same size.

### Median-of-three partition

| Case | Input type | Time complexity | Recursion depth | Notes |
|------|-----------|-----------------|-----------------|-------|
| Worst case | Specific adversarial patterns | O(n²) | O(n) | Rare in practice; requires a crafted input |
| Sorted input | Already sorted (asc or desc) | O(n log n) | O(log n) | Median of first/mid/last is the middle element — perfect split |
| Average case | Random | O(n log n) | O(log n) | Slightly better constants than default due to better pivot selection |

Median-of-three eliminates the sorted-input pathology entirely. You should see this
clearly in `output.md`: the sorted-input times for `median-of-three` will be
comparable to (or faster than) the random-input times, while the sorted-input times
for `default` will blow up for large n.

### Space complexity

Both partition strategies use O(1) extra space for the partition step itself. The
overall space complexity is dominated by the recursion stack:

| Case | Stack depth | Stack space |
|------|------------|-------------|
| Average (random input) | O(log n) | O(log n) |
| Worst case (sorted + default) | O(n) | O(n) |

For n = 10,000,000 with the default partition on sorted input, the recursion goes
10,000,000 levels deep — which is why the enlarged stack configuration is essential.

## Running the Benchmark

```shell
python benchmark.py
```

The script runs all four configurations against every file in `test_input/`, prints
progress, and writes results to `output.md`:

```
[1/64] Python (default)              n=           1  random
[2/64] Python (median-of-three)      n=           1  random
...
[64/64] Java (median-of-three)       n=  10,000,000  sorted

Results written to output.md
```

`output.md` contains two tables (random input and sorted input), with one row per
configuration and one column per input size.

> **Note:** The 10-million sorted files with `--partition default` are the worst-case
> O(n²) inputs. These runs may take several minutes each.
